# Phase 4 — Trusted Offline PMTiles Catalog / Release Contract

Status: **CODE UNDER TEST; NO APPROVED PRODUCTION CATALOG OR GEO DATA**.

## Purpose / trust boundary

NaviTaxi must never turn an arbitrary URL or a self-attested JSON manifest into a
downloadable map package. A catalog is **approved only when its exact UTF-8 bytes
match an independently reviewed SHA-256 pin**. HTTPS alone is not provenance;
the pin must come from a trusted project release/update procedure, never a hash
published inside the same untrusted JSON. The Android offline manager's
`startRemote(catalog, packageId, allowMobileData)` requires a
`TrustedOfflineCatalog` generated by `OfflineCatalogVerifier.verify`.

No pin, production catalog, PMTiles for real roads or user-visible region download
has been added in this change. No automatic background version checks are enabled.

## Exact JSON format

Top-level object keys (no extras):

```json
{
  "format": "navitaxi-offline-catalog/v1",
  "published_at": "2026-11-14T15:00:00Z",
  "packages": []
}
```

The above is **only an empty contract example**; it is not a remotely published
approved catalog. No download URL, map claim or geographic coverage is implied.

Each package object must have **exactly** these fields:

| Key | Meaning |
| --- | --- |
| `id` | Stable lowercase package identifier, safe as an Android file name |
| `version` | Source-declared version (not lexicographically compared) |
| `release_sequence` | Positive, monotonically increasing 64-bit integer for anti-rollback |
| `url` | Reviewed HTTPS PMTiles archive URL, without user-info/query/fragment |
| `size_bytes` | Declared PMTiles length: 127–2,000,000,000 bytes |
| `sha256` | Lowercase SHA-256 of the exact PMTiles archive bytes |
| `license` | Provenance/license text; a nonblank value alone is not a legal approval |
| `source_uri` | Plain HTTPS link to underlying data source and licensing evidence |
| `is_real_map` | Explicit Boolean, only true after review of actual geography |
| `has_verified_speed_limits` | Must be `false` for PMTiles-only catalogs |
| `has_verified_signs` | Must be `false` for PMTiles-only catalogs |

The road speed limit/sign database has a **different** source-evidence chain
(`data/road_intelligence/schema.sql`). PMTiles metadata must not establish legal
speed limits or survey coordinates by assertion. Real observations must be
separately verified under Road Intelligence.

Catalog gate rejects duplicate IDs, unexpected fields, invalid dates, unsafe
version/path syntax, invalid hashes/lengths, public OSM tile infrastructure and
unapproved protocols. No GPS data, auth tokens or public bulk-tile downloads.

## Release discovery/update (offline, explicit only)

`TrustedOfflineCatalog.status(packageId, installedRelease)` reports:
`NOT_INSTALLED`, `CURRENT`, `UPDATE_AVAILABLE`, `ROLLBACK_REJECTED`
or `SAME_SEQUENCE_CONFLICT`. Status compares `release_sequence` as an integer
and treats equal-sequence changes to version/hash as a conflict.

This is *decision logic only*: it does not automatically download or install a
release. The installed release sequence still needs durable storage/reconciliation
when an actual approved release catalog is supplied. An unknown prior installed
sequence must not be silently compared using string versions.

## Verify a reviewed catalog locally

```bash
sha256sum /path/to/reviewed-catalog.json
# Obtain an approved SHA-256 pin from the separate trusted release process.
python3 scripts/validate_offline_catalog.py \
  --catalog /path/to/reviewed-catalog.json \
  --approved-sha256 <approved-64-character-lowercase-SHA256> \
  --report build/offline-catalog-report.json
python3 -m unittest discover -s tests -v
```

The command never fetches third-party tiles or contacts a server. Its report has
`download_enabled=false`, `road_speed_records_verified=0` and
`traffic_signs_verified=0`. Do not use the command output to claim field
verification or a sign-off that has not happened.

## Remaining blockers / acceptance

1. Identify lawful, redistribution-compatible road-geography PMTiles sources and
   document the exact original OSM extract / license before approving a pin.
2. Store independently approved catalog pin and installed release sequence safely.
3. Connect catalog discovery/update UI only after approved real packages exist.
4. Validate failed downloads, changed ETags, storage loss and process deaths on
   Android hardware/OEM variants (emulator results are insufficient for fleet SLA).
5. Audit any actual speed/sign dataset with exact paths, SHA-256, SQLite table
   structure, WGS84 coordinates, source license and field-verification evidence.
