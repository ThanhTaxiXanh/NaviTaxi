# Road Intelligence — Independent Approval Gate (Phase 4 hardening)

**Status:** Implemented as an untrusted-data gate; CI acceptance is required on PR #15. **Zero** authoritative speed-limit
records and **zero** field-confirmed physical traffic-sign coordinates are
shipped. The complete Road Intelligence domain remains **BLOCKED** on lawful
source data and independent field verification; Phase 5 is not started.

## Why the earlier source_id test was insufficient

`RoadIntelligenceRepository.kt` formerly displayed rows if a SQLite database
existed in private storage and joined `data_sources` with nonempty
`license`/`source_uri`. Those strings are editable by whoever supplies the
database. A plausible `maxspeed` or `traffic_sign` tag is not proof of an
actual enforceable limit, correct lane/direction or a surveyed sign position.

## New fail-closed checks

1. The canonical runtime path is
   `<application-files>/road_intelligence/road_intelligence.db`. No approved
   DB is currently present inside the APK or installed by NaviTaxi.
2. `RoadDatabaseApprovalGate` checks a maximum-size immutable SQLite file
   against an independently code-reviewed SHA-256 allowlist. It rejects
   unpinned files and unpinned `-wal`/`-shm`/`-journal` sidecars.
3. Each pinned release has **separate** `approvedSpeeds` and
   `approvedSigns` flags; authorization for one does not cover the other.
4. `RoadIntelligenceRepository` returns empty GeoJSON and zero counts without
   a matching approval. Records also need `observed_at`, `verified_at`,
   legal source metadata, valid coordinates and geometry before display.
5. `RoadIntelligenceApprovedPins.entries` is deliberately EMPTY. No
   manifest stored next to a DB, no downloaded JSON and no `data_sources`
   string can add an approval or turn on speed/sign alerts.
6. A file hash authenticates approved bytes only. Human/independent review of
   applicable traffic law, measured sign position, travel direction, timestamp,
   license and derivative database obligations is STILL REQUIRED. Neither
   this code nor the candidate-audit script performs that field verification.

## Candidate review script (offline; does not produce an approval)

From repository root:

```bash
python3 scripts/initialize_road_db.py --output build/candidate-empty.db
python3 scripts/review_road_candidate.py \
  --db build/candidate-empty.db --out build/road-candidate-report.json
python3 -m unittest discover -s tests -v
python3 scripts/audit_road_assets.py \
  --root . --out build/road-assets-report.json
python3 scripts/package_road_data.py \
  --root . --output build/road-sign-speed-assets.zip
```

If a **lawfully inspectable source APK** is explicitly available, use the
existing optional `--apk /absolute/path/to/source.apk` on the latter two
commands. Otherwise do not invent any APK paths. The ZIP has the exact project
or APK-relative tree path, binary bytes, manifest and SHA256SUMS.

`review_road_candidate.py` checks canonical SQLite schema v1, checksum,
`PRAGMA integrity_check`, foreign keys, RTree consistency, WGS84 coordinates,
GeoJSON LineStrings, speed ranges, directions, dated observations and source
metadata. It emits one of `REJECTED`, `EMPTY_DATABASE` or
`CANDIDATE_REQUIRES_INDEPENDENT_FIELD_REVIEW`. All states output
`driver_speed_alerts_allowed: false` and
`physical_sign_alerts_allowed: false`; the report is **never** a trust pin.

## Genuine data candidate research, not imported

- OpenStreetMap Vietnam Geofabrik extract: https://download.geofabrik.de/asia/vietnam.html .
  This is a geographic road-data candidate under ODbL, **not** a published
  legal-speed or sign-survey dataset. No remote PBF downloaded in this PR.
- OSM `maxspeed` and `maxspeed:conditional` are different constraints and
  can be incomplete; advisory speeds are not enforceable legal speed limits:
  https://wiki.openstreetmap.org/wiki/Speed_limits
- OSM `traffic_sign` may be attached to a node (possible physical coordinates)
  or a way (a section, not a physical sign point). No conversion of a way's
  centroid into a physical road sign is permitted:
  https://wiki.openstreetmap.org/wiki/Key:traffic_sign

## Required independent acceptance before any production pin

Record source snapshot URI, SHA-256, ODbL/other redistribution license,
source object identifiers, road direction and vehicle class, actual
`speed_kmh` legal applicability and date, and each physical traffic-sign
WGS84 lat/lon plus direction, `sign_code`, survey/validation evidence and
reviewer. Validate the SQLite audit and inspect the exact generated bytes;
review each domain separately. Add the approved digest and domain flags only
through a code-reviewed release with Android regression testing. Never
automatically trust source metadata from inside the unapproved SQLite itself.

**No driving alerts are activated by this work.** This is a security and
data-quality prerequisite for future Road Intelligence, not Phase 11
completion, 34-province coverage or on-road validation.


## Spatial precision check on candidate database (2026-11-15)

The offline `scripts/review_road_candidate.py` audit now requires each road
segment's stored min/max longitude/latitude to agree with the actual GeoJSON
LineString vertex extrema within 1e-8 degrees. An expanded bounding box is
not an acceptable road geometry claim. For both sign point RTree and road RTree
entries, indexed coordinates must agree with their source SQLite values within
the float32 outward rounding required by SQLite RTree (a conservative two-ULP
bound at each coordinate). An arbitrary 0.001-degree tolerance would allow
roughly 111 m of latitude displacement and is not acceptable for physical-sign
mapping. Synthetic negative/positive cases verify the distinction.

These checks are purely mechanical consistency checks; they do not validate
instrument calibration, GPS fix, physical sign existence, traffic direction,
vehicle/legal applicability or independent publisher approval. Sign/speed release
SHA pins remain empty and alerts remain blocked.
